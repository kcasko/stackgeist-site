# From 81 to 100: fixing StackGeist's mobile Lighthouse in two PRs

StackGeist was sitting at **81 mobile performance** on Lighthouse. The whole 19-point gap came from one thing: the hero images were huge PNGs served without a priority hint. This is the diff, the numbers, and the pattern.

- Homepage hero: **perf 81 -> 100**, **LCP 4.9 s -> 1.5 s**.
- Setup pages (SetupHero component): **perf 81 -> 99**, **LCP 5.0 s -> 1.7 s**.
- The worst offender (a 657 KB PNG) drops to a **7.9 KB AVIF** at the size actually rendered.
- Zero framework changes, zero re-architecting. Two PRs, one component refactor, one sharp script.

## The diagnosis

Lighthouse mobile, simulated 4G, headless Chrome against `https://stackgeist.dev/`:

| Metric | Before | Score |
|---|---|---|
| Performance | 81 | — |
| LCP | 4.9 s | 0.29 |
| FCP | 1.6 s | 0.94 |
| Total Blocking Time | 0 ms | 1.00 |
| Cumulative Layout Shift | 0 | 1.00 |
| Speed Index | 2.7 s | 0.96 |

Read the shape. TBT is 0, CLS is 0, Speed Index is fine. That is a site whose HTML, CSS, and JS discipline is already in order. The whole loss is on LCP. Lighthouse's own opportunities agreed:

    image-delivery-insight: est savings of 571 KiB
      -> stackgeist.dev/setups/budget-gaming-desk.png     459.6 KB  (446.5 KB waste)
      -> stackgeist.dev/gear/clamp-on-led-desk-lamp.jpg   145.4 KB  (130.2 KB waste)
    lcp-discovery-insight:
      -> priorityHinted: false   (LCP <img> had no fetchpriority)
      -> renderBlocking: false   (nothing blocking, so hinting = fast)

Two things at once. The LCP image was a PNG where AVIF would be tens of KB, and the browser had no signal it should download the LCP tile first. It ends up racing against every other card image.

## The fix, in two moves

### Move 1: generate modern-format variants next to the originals

Astro's `<Image>` component works on things imported from `src/assets/`. StackGeist ships its illustrations under `public/`, which Astro treats as pass-through. Rather than restructure the tree, keep the originals where they are and generate siblings.

`scripts/build-hero-variants.cjs` (homepage) and `scripts/build-setup-hero-variants.cjs` (setup pages) do exactly this. They read four inputs each and emit AVIF + WebP at two widths (400/800 for the homepage cards, 600/1200 for the full-width setup hero). No pipeline, no config, no Astro integration. Just sharp.

Numbers you can quote:

    budget-gaming-desk.png    448.8 KB   ->  4.0 KB AVIF (400w)
    small-bedroom-gaming.png  656.9 KB   ->  7.9 KB AVIF (600w)
    clamp-on-led-desk-lamp.jpg 142.0 KB  ->  8.2 KB AVIF (400w)

The originals stay because they are still the `<img>` fallback for the ~1% of clients without AVIF or WebP.

### Move 2: <picture> with a proper fetchpriority

The homepage hero grid was:

    <img src={q.img} alt="" loading="eager" decoding="async" />

Every card marked eager, none marked priority, and PNG-only. That became:

    <picture>
      <source type="image/avif" srcset={`${q.base}-400w.avif 400w, ${q.base}-800w.avif 800w`}
              sizes="(min-width: 960px) 25vw, (min-width: 560px) 50vw, 100vw" />
      <source type="image/webp" srcset={`${q.base}-400w.webp 400w, ${q.base}-800w.webp 800w`}
              sizes="(min-width: 960px) 25vw, (min-width: 560px) 50vw, 100vw" />
      <img src={q.fallback} alt="" width="800" height="450"
           loading={i === 0 ? 'eager' : 'lazy'}
           fetchpriority={i === 0 ? 'high' : 'auto'}
           decoding="async" />
    </picture>

Three things earn the score:

1. **AVIF first, WebP second.** Modern Chromium + Firefox pick AVIF; Safari picks WebP; everything else falls back to raster.
2. **Only the first card is `fetchpriority="high"`** and `loading="eager"`. The rest are lazy. Marking every card eager without a priority is worse than marking only the LCP eager.
3. **Explicit `width` and `height`** on the fallback `<img>`. That is what keeps CLS at 0 while the responsive `srcset` picks the right variant.

For the setup pages the change was in `SetupHero.astro` — one component, four pages fixed automatically.

## The result

Local Lighthouse against the built `dist/`, mobile, simulated 4G, headless Chrome:

|              | homepage before | homepage after | setup before | setup after |
|--------------|-----------------|----------------|--------------|-------------|
| Performance  | 81              | **100**        | 81           | **99**      |
| LCP          | 4.9 s           | **1.5 s**      | 5.0 s        | **1.7 s**   |
| FCP          | 1.6 s           | 1.5 s          | 1.6 s        | 1.7 s       |
| Speed Index  | 2.7 s           | 1.5 s          | 2.5 s        | 1.7 s       |
| CLS          | 0               | 0              | 0            | 0           |

Field data (Cloudflare RUM, and Chrome UX Report for Search Console) aggregates over 28 days, so ranking-visible impact takes 3-4 weeks to catch up. But the lab number is where a hiring manager or a search-engine crawler forms an opinion, and that number moved today.

## What did not move the needle

Every diagnosis in the report pointed at the LCP image. I did not touch, and did not need to touch:

- Server response time (already ~120 ms — Cloudflare Pages on the edge).
- Render-blocking CSS (only 3.3 KB of it, negligible).
- JS bundle (TBT was already 0 — Astro's islands architecture pays off here).
- Font loading, third-party scripts, preconnect hints.

The point: don't scatter effort. When one metric fails and the rest pass, fix the one metric. StackGeist's Astro + Cloudflare foundation was already good; the score was hostage to one file.

## Route audit — what did NOT need fixing

After #2 and #3 landed, I measured seven more route families on the live site to confirm no other page was silently 81. Every remaining route was already 99 perf, LCP 1.6s. StackGeist's baseline is already good; the two hero images were the whole story.

    /                             81 -> 100 (PR #2)   LCP 4.9s -> 1.5s
    /setups/<slug>                81 -> 99  (PR #3)   LCP 5.0s -> 1.7s
    /gear/               (index)  99                  LCP 1.6s
    /gear/desk-lighting/          99                  LCP 1.6s
    /gear/budget-tech/            99                  LCP 1.6s  (717 KB Amazon-hosted image waste, out of scope)
    /kits/               (index)  99                  LCP 1.6s
    /kits/<slug>                  99                  LCP 1.6s
    /guides/<slug>                99                  LCP 1.6s

The one flag on `/gear/budget-tech/` is Amazon-hosted product imagery. Fixing it would require self-hosting the images, which touches editorial policy (Amazon PA-API terms + affiliate compliance), not just performance. Deliberately out of scope.

## The reusable pattern

For any Astro (or plain HTML) site serving hero images from `public/`:

1. Run Lighthouse. If LCP is the only failing metric, this pattern applies.
2. Write a sharp script that generates AVIF + WebP variants at the two widths you actually render.
3. Swap the `<img>` for a `<picture>` with `<source>` for each format.
4. Mark exactly one image `fetchpriority="high"` + `loading="eager"`. Lazy everything else.
5. Keep the raster fallback and explicit dimensions so CLS stays at zero.

Two PRs, thirty minutes of hands-on time each, two new files, one component refactor. That is the whole story.
